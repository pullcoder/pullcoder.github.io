## 2. 프로그램 동작 순서

```
① 사용자 명령 (음성 → 서버 STT로 텍스트 / 또는 글자 입력)
② 대화(chat) → 명령 속 앱 이름(폰 안에서 찾음)이 있고 그 앱에서 할 일이면 대상 앱 열기
③ 대상 앱 열기 → 서버가 명령 검사 (패키지명·버전만 보냄, 화면은 읽지 않음 — 계정 변경·금융·대화 앱 거부)
④ 승인 카드: 목표 · 대상 앱 · 멈추는 조건 → 사용자가 [실행] 직접 터치
⑤ 단계 반복 (최대 20단계)
     화면 구조 읽기 → 서버: 레시피로 다음 동작 1개 결정 (galaxy 빌드는 레시피가 없으면 로컬 LLM → 클라우드 LLM)
     → 앱: 민감 동작 재검사 → 포인터 표시 → 누르기·입력·스크롤 → 화면이 멈출 때까지 대기
     (지점·옵션 선택이 필요하면 선택 카드로 질문)
⑥ 완료 / 결제 직전 정지 / 터치로 중단 → 결과 카드 + 작업 기록·녹음 저장
```

화면 구조는 단계마다 서버로 보낸 뒤 **즉시 폐기**됩니다 (처리방침 3장).

## 3. 제기된 문제점 검토

| # | 문제점 | 현재 | 판단 · 보완 |
| :---: | --- | --- | --- |
| 1 | **더미 데이터 삭제**, 실제 서비스로 전환 | 더미 배달·금융 앱 2개 | 전환은 맞습니다. 다만 더미 앱은 **삭제보다 출시 빌드에서 빼고 개발용으로 남기기**를 권합니다. 실제 앱으로만 확인하면 실제 주문 위험, 앱 업데이트마다 결과가 달라 비교 불가, 약관 문제가 있습니다. → [D1](#5-결정-대기) |
| 2 | **TTS 미구현** | Typecast 코드만 있음 | 기본값을 **기기 내장 TTS**(Android `TextToSpeech`)로 두기를 권합니다. 무료, 즉시 동작, 국외 이전 없음. Typecast는 고품질 옵션으로 유지 → **결정은 Typecast 기본** ([D6](#5-결정-대기)) |
| 3 | **화면 캡처본으로 학습** (어디를 어떻게 눌러 들어갈지) | 이미지가 아니라 **UI 구조(텍스트 트리)** 를 사용 | 이미지에는 알림·주소·카드 번호 일부 등 화면의 모든 것이 담기고, 처리방침의 "즉시 폐기"와 제3자 앱 화면 저장(약관·저작권)에 걸립니다. **UI 구조 + 고른 요소 + 결과**를 마스킹해 **동의한 사용자만** 저장하는 방식을 권합니다. 이미지는 접근성 정보가 없는 앱에 한정 → [D2](#5-결정-대기) |
| 4 | **어떤 데이터를 저장해 학습할지** | 없음 | 학습 샘플 = 목표, 앱 패키지·버전, 화면 요소(개인정보 마스킹), 고른 동작, 결과(성공·실패·사용자 중단·사용자 선택), 소요 시간. 정답은 "성공한 실행 경로"와 "사용자가 멈춘 지점" |
| 5 | **사용자 음성 저장** (STT → 문서만 되는가?) | 원본 m4a + 인식 텍스트 모두 저장됨 | 문서만 남는 것이 아닙니다. 음성 원본은 개인 저장 공간(1인 500MB)에, 텍스트는 대화 기록에 있습니다. 추가로 필요한 것: **학습 활용 동의**(별도·철회 가능), **인식 결과 고치기 화면**(틀린 STT 교정 → STT 개선 데이터) |
| 6 | **앱 구동 최적화** | 단계마다 새 WebSocket 연결 + 화면 안정 대기 0.3초 + LLM 추론 | 연결 재사용, 화면 요소 압축(보이지 않거나 중복된 요소 제거), 로컬 모델 양자화, 자주 쓰는 경로 저장 후 재생(레시피) |
| 7 | **LLM 튜닝** | 프롬프트만 | 순서: ① 프롬프트 + 앱별 가이드 → ② **평가셋** 구축 → ③ 수집 데이터로 LoRA 미세조정(exaone3.5 등) → ④ 평가 후 교체. 데이터·평가셋 없이 튜닝부터 하면 좋아졌는지 알 수 없습니다 |
| 8 | **동작 확인이 안 됨** (TTS 없음, 대화 기록 없음) | 기록은 저장되지만 단계별 내용을 볼 곳이 없음 | **실행 기록 상세 화면**(단계별 설명, 사용한 LLM, 멈춘 이유)과 결과 음성 안내가 먼저 필요합니다 |
| 9 | **기본 베이스** (음식 주문·여행·교통 예약) | 없음 | 분야별 필수 정보(슬롯)와 즐겨찾기 → [6장 Phase 10](#phase-10-분야별-기본-베이스) |

## 5-1. 규제·스토어 정책 점검 (2026-10-12)

### Google Play 접근성 API 정책 — 설계 변경

Google Play는 접근성 API를 **"스스로 동작을 시작·계획·실행하는 앱"** 에 쓰는 것을 금지하고, **"사람이 미리 정한 고정 스크립트에 따르는 결정적·규칙 기반 자동화"** 만 허용합니다 ([정책](https://support.google.com/googleplay/android-developer/answer/10964491)). 목표 승인 후 LLM이 화면마다 다음 동작을 정하는 지금 방식은 금지 대상에 해당할 가능성이 높습니다. 갤럭시 스토어 배포 가이드에는 이런 조항이 없습니다 ([가이드](https://developer.samsung.com/galaxy-store/distribution-guide.html)).

**결정: 엔진 하나, 빌드 둘**

| | 레시피가 있는 앱 | 레시피가 없는 앱 |
| --- | --- | --- |
| 공통 엔진 | **레시피 실행**: 앱별 실행 순서를 사람이 작성(`ai-server/recipes/`). 말하면 자동 실행, 예상과 다른 화면이면 멈춤 | — |
| **galaxy** 빌드 (갤럭시 스토어) | 레시피 실행 | **허용 앱 목록 안에서만** LLM 단계 실행 (`mode: agent`, D8) |
| **play** 빌드 (Google Play) | 레시피 실행 | 실행하지 않음 → 이후 **위치 안내**(사용자가 직접 누름) |

- 갤럭시 기본 기능(Gemini 작업 자동화·AppFunctions·Bixby)은 지금 다른 앱이 호출할 수 없음. Android 17에서 개발자 공개가 예정되어 있으므로 열리면 접근성 API 대신 공식 경로로 전환 검토
- 한국 법은 어느 스토어든 똑같이 적용
